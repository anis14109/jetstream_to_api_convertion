  57 |    **access token** (short lived) and a **refresh token** (long lived, rotated).
  58 | 2. Send the access token as `Authorization: Bearer <token>` on protected routes.
  59 | 3. When the access token expires, call `POST /api/v1/auth/refresh` with the
  60 |    refresh token to get a new pair. Refresh tokens rotate on every use.
  61 | 4. Presenting a refresh token that has already been rotated revokes the whole
  62 |    token family and the session (`TOKEN_REUSED`).
  63 | 
  64 | See [authentication.md](authentication.md) for the full lifecycle.
  65 | 
  66 | ## Versioning policy
  67 | 
  68 | - The version lives in the URL path (`/api/v1`). `config('api.version')`
  69 |   controls the documented version.
  70 | - Breaking changes ship as `/api/v2`; `v1` stays supported in parallel.
  71 | - Additive changes (new optional fields, new endpoints) do not bump the version.
  72 | 
  73 | ## Conventions
  74 | 
  75 | - **Timestamps** are ISO-8601 UTC strings (`2026-09-17T12:00:00.000000Z`).
  76 | - **Identifiers** of synchronizable resources are ULIDs (26 chars, sortable).
  77 | - **Users** keep their integer primary key (`id`).
  78 | - **Pagination** uses opaque cursors, never offsets (`cursor`, `next_cursor`).
  79 | - **Errors** should be handled by branching on `code`, never on `message`.

#### 3.11.7 `docs/api/sync.md`  (151 lines)

````markdown
   1 | # Offline-First Synchronization
   2 | 
   3 | The sync engine lets clients work offline and reconcile later without losing
   4 | data or silently overwriting newer server state.
   5 | 
   6 | ## Concepts
   7 | 
   8 | - **Revision** â€” a monotonically increasing integer. Every write appends an
   9 |   entry to the `change_logs` journal and the entry's auto-increment `id` is the
  10 |   revision. Clients must never use their own clock; the cursor is server time.
  11 | - **Cursor** â€” the highest revision a client has consumed. The cursor is stored
  12 |   server-side per client (keyed by the auth session id, or the access token id
  13 |   for programmatic tokens) so a client that loses its local state can recover.
  14 | - **Version** â€” a per-record optimistic-concurrency counter on `students`. It is
  15 |   independent of the global revision.
  16 | - **Operation id** â€” a client-generated idempotency key for a push operation.
  17 |   Replaying the same `operation_id` never applies the operation twice.
  18 | 
  19 | ## Endpoints
  20 | 
  21 | All three require authentication and use the `api-sync` rate limit.
  22 | 
  23 | ### `GET /sync/cursor`
  24 | 
  25 | Returns the last revision this client pulled.
  26 | 
  27 | ```json
  28 | { "success": true, "message": "Sync cursor.", "data": { "cursor": 42, "server_time": "..." } }
  29 | ```
  30 | 
  31 | A new client starts at `0`.
  32 | 
  33 | ### `GET /sync/pull?cursor=0&limit=200`
  34 | 
  35 | Returns journal entries **after** `cursor`, in revision order. `limit` defaults
  36 | to `SYNC_PULL_BATCH_SIZE` (200) and is capped at 1000. Pulling advances the
  37 | stored cursor to `next_cursor`.
  38 | 
  39 | ```json
  40 | {
  41 |   "success": true,
  42 |   "message": "Changes pulled.",
  43 |   "data": {
  44 |     "changes": [
  45 |       {
  46 |         "revision": 41,
  47 |         "entity_type": "student",
  48 |         "entity_id": "01JABC...",
  49 |         "operation": "updated",
  50 |         "version": 3,
  51 |         "data": { "id": "01JABC...", "name": "Alice v3", "version": 3 },
  52 |         "server_time": "2026-09-17T12:00:00.000000Z"
  53 |       }
  54 |     ],
  55 |     "next_cursor": 41,
  56 |     "has_more": false,
  57 |     "server_time": "2026-09-17T12:00:00.000000Z"
  58 |   }
  59 | }
  60 | ```
  61 | 
  62 | `operation` is `created`, `updated` or `deleted`. Deleted entries carry a
  63 | tombstone `data` payload (`id`, `version`, `deleted_at`).
  64 | 
  65 | Keep calling while `has_more` is `true`, passing the returned `next_cursor`.
  66 | 
  67 | ### `POST /sync/push`
  68 | 
  69 | Applies a batch of client operations atomically. Up to
  70 | `SYNC_MAX_OPERATIONS_PER_PUSH` (200) operations per request.
  71 | 
  72 | ```json
  73 | {
  74 |   "operations": [
  75 |     {
  76 |       "operation_id": "01JOPCLIENT0000000000000001",
  77 |       "entity_type": "student",
  78 |       "entity_id": "01JABC...",
  79 |       "operation": "create",
  80 |       "data": { "name": "Bob", "email": "bob@example.com" }
  81 |     },
  82 |     {
  83 |       "operation_id": "01JOPCLIENT0000000000000002",
  84 |       "entity_type": "student",
  85 |       "entity_id": "01JDEF...",
  86 |       "operation": "update",
  87 |       "version": 2,
  88 |       "data": { "name": "Alice v3" }
  89 |     },
  90 |     {
  91 |       "operation_id": "01JOPCLIENT0000000000000003",
  92 |       "entity_type": "student",
  93 |       "entity_id": "01JGHI...",
  94 |       "operation": "delete",
  95 |       "version": 1
  96 |     }
  97 |   ]
  98 | }
  99 | ```
 100 | 
 101 | Rules:
 102 | 
 103 | - `entity_type` must be `student`.
 104 | - `operation` is `create`, `update` or `delete`.
 105 | - `version` is required for `update` and `delete`.
 106 | - `data.name` is required for `create` and `update`.
 107 | 
 108 | Success response (`200`):
 109 | 
 110 | ```json
 111 | {
 112 |   "success": true,
 113 |   "message": "Sync push processed.",
 114 |   "data": {
 115 |     "applied": [
 116 |       { "operation_id": "...", "entity_type": "student", "entity_id": "01JABC...", "operation": "create", "version": 1, "revision": 42, "server_time": "..." }
 117 |     ],
 118 |     "conflicts": [],
 119 |     "replayed": [ { "...previously stored response..." } ],
 120 |     "latest_revision": 42,
 121 |     "next_cursor": 42,
 122 |     "server_time": "..."
 123 |   }
 124 | }
 125 | ```
 126 | 
 127 | If **any** operation conflicts, the whole request returns `409 SYNC_CONFLICT`
 128 | with the conflict list in `data.conflicts`. Each conflict includes
 129 | `reason`, `client_version`, `server_version` and `server_data`:
 130 | 
 131 | | `reason` | Meaning |
 132 | |----------|---------|
 133 | | `version_mismatch` | The record changed on the server since the client read it |
 134 | | `already_exists` | A `create` collided with an existing id |
 135 | | `missing` | The record does not exist on the server |
 136 | | `deleted` / `already_deleted` | The record was deleted before this operation |
 137 | 
 138 | Non-conflicting operations that were applied before the conflict in the same
 139 | batch are still committed (the batch is processed inside a transaction but
 140 | conflicts are collected, not thrown, so partial progress is preserved and
 141 | reported).
 142 | 
 143 | ## Recommended client loop
 144 | 
 145 | 1. `GET /sync/cursor` on startup (or use the locally stored cursor).
 146 | 2. `GET /sync/pull` repeatedly until `has_more` is false; apply changes locally
 147 |    and store `next_cursor`.
 148 | 3. Queue local writes with a stable `operation_id`.
 149 | 4. `POST /sync/push` the queue. On `200`, drop applied/replayed operations.
 150 | 5. On `409`, merge each conflict (usually `server_data` wins) and re-queue.
 151 | 6. Repeat.
